# 响应时间统计说明

本文档说明当前系统对响应时间的统计方式，以及影响**首字响应时间**（Time to First Token / 首包时间）的主要因素。

---

## 1. 首字响应时间定义

**首字响应时间**：从客户端发起请求开始，到客户端收到**第一个流式数据包**（第一个 SSE 事件或 RunContent 片段）为止的耗时。

该指标直接影响用户感知的“回答是否够快”；在流式接口下，首包越早到达，体验越好。

---

## 2. Agno 提供的首字耗时（结束后可读）

Agno 框架在 run 结束后会填充 **Metrics**，其中包含 **`time_to_first_token`**（单位：秒），即模型从开始生成到首个 token 产出的耗时，可用于衡量首字响应中的“模型首 token”部分。

- **文档**：[Agno Metrics](https://docs.agno.com/reference/agents/metrics) 中定义 `time_to_first_token`：*Time until the first token is generated (in seconds)*。
- **层级**：
  - **Run 级**：`RunOutput.metrics.time_to_first_token`（整次 run 的汇总）。
  - **Message 级**：每条 assistant 等消息可有 `message.metrics.time_to_first_token`（该条消息的首 token 耗时）。

**获取方式（结束后）：**

1. **流式场景**：收到 **`RunCompleted`** 事件时，事件 payload 中通常包含本次运行的完整结果与统计信息；若 AgentOS 将 RunOutput 序列化进该 payload，则可从其中的 `metrics.time_to_first_token` 或 `messages[].metrics.time_to_first_token` 读取。
2. **历史查询**：调用 **GET /sessions/{session_id}/runs** 获取某会话的 run 列表时，每个 run 对象中会包含 `metrics`（及可选的 `messages`）；从 `run.metrics.time_to_first_token` 或某条 `message.metrics.time_to_first_token` 读取。
3. **非流式 / 直接调用**：若通过 `agent.run(...)` 同步调用，则 `run_response.metrics.to_dict()` 及 `run_response.messages[i].metrics.to_dict()` 中会包含 `time_to_first_token`（若模型/提供商有上报）。

注意：该字段是否存在取决于模型与 Agno 版本，部分 run 可能无此字段。

---

## 3. 当前已统计的时间项

系统在以下位置使用 `time.perf_counter()` 进行耗时统计，并输出到日志（agno 日志或 `agentos.request`）。

| 统计项 | 含义 | 日志位置/关键字 |
|--------|------|----------------|
| **header_ready_ms** | 流式：从请求进入到 `call_next` 返回（响应头/对象就绪，body 尚未写出） | `agentos.request`：`Stream started: ... header_ready_ms=... request_id=...` |
| **stream_complete（总耗时）** | 流式：从请求进入到流传输结束（finally）的毫秒数 | `agno`：`stream_complete request_id=... \| ... total_ms=... ttfb_ms=...` |
| **非流式请求总耗时** | 非流式：单次请求从进入到响应返回的毫秒数 | `agentos.request`：`Response: ... in ...ms request_id=...` |
| **品类标准化阶段耗时** | 从首次调用 `search_category_by_name` 到该阶段最后一次调用结束的墙钟时间 | `tool_hooks`：`品类标准化阶段完成 \| 阶段耗时: X.XXs` |
| **查询商品库阶段总时间** | 从首次 `query_brand_by_category` 到进入 `build_review_fields` 的墙钟时间 | `tool_hooks`：`查询商品库阶段完成 \| ... 总时间 Xms` |
| **查询商品库阶段纯耗时** | 各次 `query_brand_by_category` 执行时间之和（不含中间 think 等） | 同上：`（查询纯耗时：Xms）` |
| **阶段结束到首包** | 从“查询商品库阶段”结束到流式首 chunk 的秒数 | `agno`：`request_id=... 查询商品库阶段结束到首包: X.XXs`（与 stream_complete 同 request_id 关联） |
| **单次工具耗时** | 每次工具调用的执行时间（秒） | `tool_hooks`：`[TOOL_CALL] ... 耗时: X.XXXs`（DEBUG level=2）；更完整的工具调用序列与状态以 Agno 自身日志为准，无需重复记「工具链路」起止。 |

说明：

- 流式场景下：**不要**把 `Stream started` 的 `header_ready_ms` 当作整次请求完成时间；整次传输结束以 **`stream_complete`** 一行的 `total_ms` 为准（同一 `request_id` 可 grep 关联）。
- 若流在 yield 中异常，会打 `Stream error request_id=...`；此前 `Stream started` 若已为 200，需结合 `stream_complete` 的 `error=` 排查。
- 所有耗时均基于 `time.perf_counter()`，不受系统时钟调整影响。

## 4. 请求到首包的流程概览

在典型一次 runs 流式请求中，从请求进入到首包发出，大致顺序如下：

```
请求进入中间件
    → Agent 接收消息、加载上下文
    → 阶段1：需求解析与规划（think）
    → 阶段2：节日推荐（get_festival_date_info、get_all_festivals）
    → 阶段3：品类标准化（search_category_by_name，可能多轮）
    → 阶段4：查询规划（think）
    → 阶段5：查询商品库（query_brand_by_category，可能多次）
    → 阶段6：build_review_fields（整合结果）
    → 模型生成首段内容并开始流式输出
    → 首包经中间件发出 → 客户端收到
```

首字响应时间 = 上述整条链路的总耗时（含网络与序列化）。

---

## 5. 影响首字响应时间的主要因素

### 5.1 请求与中间件

- **请求解析与路由**：Body 解析、路由匹配、中间件执行。
- **流式包装**：中间件包装流式 body 以统计首包与传输结束；对延迟影响可忽略。路径级是否打 INFO 见 `agentos.request_logging`（`skip_info_prefixes` / `always_info_prefixes`）或环境变量 `REQUEST_LOGGING_SKIP_INFO_PREFIXES`、`REQUEST_LOGGING_ALWAYS_INFO_PREFIXES`。

### 5.2 需求解析与规划（阶段 1）

- **think 调用**：模型推理时间与思考长度；可能多次 think。
- **历史加载**：若启用记忆，从 DB 加载会话/历史会带来一定延迟。

### 5.3 节日推荐（阶段 2）

- **get_festival_date_info**：本地或少量计算，通常较短。
- **get_all_festivals**：全量节日数据加载与返回，数据量会影响耗时。

### 5.4 品类标准化（阶段 3）

- **search_category_by_name** 单次耗时由以下组成：
  - 查询文本 **Embedding**（Qwen Embedding API 调用）
  - **Milvus** 向量检索（top_k 等）
  - 若开启 **Rerank**：Qwen Rerank API 调用
- **调用次数**：工作流可能多轮调用（含回退细化），每轮都会增加延迟。
- **配置**：`top_k`、`top_n`、`enable_rerank`、`timeout` 等（见 `query_normalization` 配置）会影响单次耗时与稳定性。

该阶段在日志中对应：**品类标准化阶段完成 \| 阶段耗时**。

### 5.5 查询规划（阶段 4）

- **think / analyze**：模型根据品类结果做规划，推理时间与 prompt 长度、结果规模相关。

### 5.6 查询商品库（阶段 5）

- **query_brand_by_category**：每次调用为**外部商品库 API**（如 AI Trim 接口），受网络与上游服务影响。
- **调用次数**：品类数量与是否回退决定调用次数；次数越多，阶段总时间与“查询纯耗时”都会增加。
- 日志中可区分：
  - **总时间**：阶段墙钟时间（含 think 等）
  - **查询纯耗时**：仅各次 `query_brand_by_category` 耗时之和。

### 5.7 结果整合与首段生成（阶段 6 到首包）

- **build_review_fields**：在内存中整合推荐与节日数据，通常较短。
- **首段模型推理**：`build_review_fields` 之后，模型生成第一段可流式输出的内容（思考或正文），这部分是“阶段结束到首包”的主要组成。
- **流式写出与传输**：首包从应用经中间件、TCP 到客户端；一般远小于前面各阶段。

日志中对应：**request_id=... 查询商品库阶段结束到首包** 与 **stream_complete** 中的 `ttfb_ms`，可用于重点优化“整合完成 → 首字发出”这一段。

### 5.8 模型与配置

- **模型选择**：不同模型首 token 延迟差异大（如流式首字延迟）。
- **stream / stream_events**：是否开启流式与事件流，影响首包内容与时机。
- **上下文长度**：历史与当前 prompt 越长，首 token 前的推理时间往往越长。

### 5.9 外部依赖与网络

- **Embedding / Rerank API**：Qwen 等服务的延迟与可用性。
- **Milvus**：向量检索的延迟与负载。
- **商品库 API**：`query_brand_by_category` 依赖的上游响应时间。

## 6. 优化首字响应时间的建议方向

| 方向 | 说明 |
|------|------|
| 减少首包前工具调用 | 在满足流程前提下，减少 think 轮次、节日/品类/查询的冗余调用。 |
| 缩短品类标准化 | 适当降低 top_k/top_n、评估 Rerank 是否必开、或缓存常见查询的标准化结果。 |
| 控制查询商品库次数与耗时 | 合并或减少 `query_brand_by_category` 调用；优化上游 API 或设置合理超时。 |
| 优化模型首 token | 选用首字延迟更低的模型或推理配置；适当控制上下文长度。 |
| 监控与定位 | 结合「品类标准化阶段耗时」「查询商品库总时间/纯耗时」「阶段结束到首包」三条日志，定位瓶颈在工具侧还是模型侧。 |
